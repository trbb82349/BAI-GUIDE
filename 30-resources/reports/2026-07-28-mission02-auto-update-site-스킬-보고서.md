# Mission 02 보고서 — "스킬을 공부해보자"를 auto-update-site로 실습한 결과

> 이 보고서는 컴퓨터공학·AI·코딩을 전혀 모르는 사람도 읽을 수 있도록 썼습니다.

## 1. 이 보고서가 다루는 것

Mission 02의 목표는 "AI에게 시키는 작업 설명서(스킬)를 어떻게 잘 쓰는가"를 익히는 것입니다.

이 작업은 사실 2026-07-24에 한 번 완료되어 [`20-areas/daily/2026-07-24-mission02-스킬-공부.md`](../../20-areas/daily/2026-07-24-mission02-스킬-공부.md)에 기술적인 기록으로 남아 있습니다. 이 보고서는 그 기록을 **초보자가 이해할 수 있는 말**로 다시 풀어 정리한 버전입니다.

## 2. "스킬"이 뭔가요? (비유)

AI에게 매번 "이렇게 해줘, 저건 이렇게 확인해줘, 이 순서로 해줘"를 처음부터 다 설명하면 번거롭고, 사람마다 설명이 달라서 결과물 품질도 들쭉날쭉해집니다.

**스킬**은 이런 반복되는 작업 하나에 대해 "① 언제 이걸 써야 하는지, ② 시작 전에 뭘 확인해야 하는지, ③ 판단이 필요할 때 어떤 기준으로 판단하는지, ④ 어떤 순서로 하는지, ⑤ 결과물이 어떤 모양이어야 하는지, ⑥ 언제 끝났다고 볼 수 있는지, ⑦ 막히면 어떻게 하는지"를 문서 하나에 미리 적어둔 **"업무 매뉴얼"** 같은 것입니다. 요리로 치면 매번 즉흥으로 요리하는 대신 레시피 카드를 하나 만들어두는 것과 비슷합니다.

## 3. "7가지 기준"이 뭔가요? (쉬운 설명)

Mission 02는 좋은 스킬 문서(SKILL.md)라면 반드시 아래 7개 항목을 담고 있어야 한다고 말합니다.

| 기준 | 쉬운 설명 |
|---|---|
| **description (트리거)** | "이 매뉴얼을 언제 꺼내 봐야 하나"를 적는 부분. 이 문서 맨 위 표지에만 적혀 있어야 AI가 항상 볼 수 있습니다. |
| **Input** | 시작하기 전에 반드시 확인해야 할 것들 (재료 체크리스트) |
| **Judgment** | 애매한 상황에서 AI가 마음대로 정하지 않도록 정해둔 판단 규칙 |
| **Steps** | 실제로 진행하는 순서 |
| **Output** | 결과물이 어떤 모양이어야 좋고, 어떤 모양이면 잘못된 것인지 |
| **QA** | "이제 끝났다"고 판단할 수 있는 체크리스트 |
| **Failure repair** | 못 끝냈을 때 어떻게 표시하고 멈춰야 하는지 |

여기서 가장 중요한 규칙 하나: **"언제 쓰나"는 반드시 표지(description)에만 적어야 한다.** 왜냐하면 AI는 본문을 스킬이 이미 실행되기로 정해진 다음에야 읽기 때문입니다. "본문 어딘가에 '이런 요청이 오면 이 스킬을 써라'라고 적어봤자, AI는 그 문장을 읽기도 전에 이미 다른 스킬을 골라버렸을 수 있다"는 뜻입니다. 그래서 트리거(언제 쓰나)는 100% description(표지)에 있어야 작동합니다.

### AI가 스킬 문서를 읽는 3단계 (왜 파일을 나누는가)

AI는 스킬 문서를 한 번에 다 읽지 않고, 아래처럼 **필요한 만큼만** 읽습니다.

1. **표지(name + description)** — 항상 보임. 여기서 "이 상황에 이 스킬을 쓸지 말지"를 결정.
2. **본문(SKILL.md 전체)** — 스킬을 쓰기로 정해진 다음에만 읽음. 500줄 정도를 넘지 않는 게 좋습니다.
3. **첨부 파일(references/, assets/ 등)** — 본문이 "지금 이거 읽어" 라고 명시적으로 시킬 때만 읽음.

이렇게 하면 안 쓰는 정보까지 매번 다 읽느라 낭비하지 않습니다. 그래서 "처음부터 폴더를 여러 개로 쪼개서 설계"하는 게 아니라, **일단 문서 하나에 다 쓰고, 넘치는 부분만 나중에 떼어내는** 순서가 맞습니다.

## 4. auto-update-site 스킬에 실제로 적용해보니

`.agents/skills/auto-update-site/SKILL.md` 문서를 7기준 구조로 다시 정리했습니다. (기존 133줄 → 97줄로 오히려 짧아짐 — 불필요한 나열이 줄었기 때문)

아래는 각 기준이 실제로 어떻게 채워졌는지, 쉬운 말로 옮긴 것입니다.

### ① description (표지, 트리거)
> "자동으로 업데이트되는 웹사이트", "주기적으로 데이터를 가져와서 보여주는 페이지", "GitHub Pages 자동 배포" 같은 말이 나오면, 사용자가 이 스킬을 콕 집어 요청하지 않아도 먼저 이 스킬을 쓴다.

→ "언제 쓰나"가 전부 표지에 있고, 본문 어디에도 "이런 요청이 오면"류의 문장이 없는지 확인했습니다(실제로 없었습니다). 이게 지켜지지 않으면 트리거 자체가 작동하지 않기 때문에 가장 먼저 확인한 항목입니다.

### ② Input (시작 전 확인 목록)
시작하기 전에 꼭 확인해야 할 5가지를 적어뒀습니다: 무엇을 보여줄지, 데이터를 어디서 가져올지, 얼마나 자주 갱신할지, GitHub 계정/저장소가 있는지, 인증(비밀번호 같은 열쇠)이 필요한지. 하나라도 안 정해졌으면 AI가 임의로 정하지 않고 먼저 물어보게 되어 있습니다.

### ③ Judgment (판단 규칙)
사람이 매번 옆에서 감독하지 않아도 AI가 스스로 안전하게 판단하도록 만든 규칙 3가지가 있습니다.
- 돈이 드는 서비스는 쓰지 않는다(전부 무료 한도 안에서 해결).
- 자동 실행 예약 시각을 "정각(예: 9시 00분)"으로 잡지 않는다 — GitHub 서버가 몰리는 시간이라 실행이 밀리거나 아예 건너뛰어진 실제 사례가 있었기 때문입니다.
- 게시판처럼 페이지를 넘겨가며 새 글만 가져오는 방식에서는 "한 페이지 안에 이미 알고 있던 글이 하나라도 섞여 있으면 그 페이지에서 멈춘다"는 안전장치를 반드시 넣는다 — 이 규칙이 없어서 실제로 몇 달 전 옛날 글까지 "새 글"로 착각해 통째로 끌려온 사고가 있었습니다.

그리고 "확실하지 않은 것은 지어내지 말고 OPEN(미확정)으로 남겨두라"는 규칙도 있습니다. 예: 데이터를 가져올 웹사이트의 이용 약관을 확인 안 했으면, 확인 전까지는 수집 코드를 완성하지 않습니다.

### ④ Steps (진행 순서)
data.json(데이터 저장 파일) 설계 → collect.py(데이터 수집 코드) 작성 → build_site.py(웹페이지 생성 코드) 작성 → update.yml(예약 실행 설정) 작성 → GitHub에 실제로 올리고 켜기, 순서로 5단계가 정리돼 있습니다. 이 중 코드를 실제로 작성하는 단계와 GitHub에 배포하는 단계에서는 "이 단계에 도달하면 템플릿/가이드 파일을 읽어라"라는 문장이 붙어 있습니다(자세한 내용은 아래 6번 참고).

### ⑤ Output (결과물 모양)
좋은 결과물 예시(폴더 구조 그림)와, 피해야 할 예시(데이터 파일 안에 `//` 같은 주석을 넣는 것 — 이러면 파일이 깨져서 사이트 전체가 멈춥니다) 한 쌍이 나란히 적혀 있습니다.

### ⑥ QA (끝났다고 보는 기준)
데이터 파일이 정상인지, 필수 빈 파일(`.nojekyll`)이 있는지, 예약 실행 시각이 정각을 피했는지, 안전장치가 들어갔는지, 실제로 한 번 수동 실행해서 성공(초록불)했는지 — 이렇게 5개 체크박스로 "끝"을 정의합니다.

### ⑦ Failure repair (막혔을 때)
모르는 항목은 `[미확인: 이유]`라고 표시하고 그 부분만 비워둔 채 나머지는 진행합니다. 그리고 실제로 자주 반복됐던 문제 5가지(저장 충돌, 페이지 404 오류, 데이터 파일 깨짐, 예약 실행이 그날만 건너뛰어짐, 페이지네이션 사고)와 각각의 해결 방법이 미리 적혀 있습니다.

## 5. 실제 프로젝트로 확인한 관찰 기록 — cron-job.org 추가 전/후 비교

7가지 기준을 문서에 다 적었다고 끝나는 게 아니라, "진짜로 이 스킬이 시키는 대로 했을 때 정말 잘 작동하는지"를 확인해야 합니다. 이번에는 가상의 시험 대신, 이 스킬로 실제로 만들어서 지금도 운영 중인 **인천대 알림 모음 사이트**(`10-projects/incheon-univ-notices`) 프로젝트에서 실제로 벌어졌던 일을 가지고 "고치기 전 / 고친 후"를 비교해봤습니다. 이게 더 확실한 증거인 이유는, 이 사건이 실제로 SKILL.md의 Failure repair 항목 하나를 만들어낸 원인이기 때문입니다.

**배경**: 이 사이트는 "매일 아침 8시쯤 GitHub이 자동으로 새 글을 가져와서 사이트를 갱신해준다"는 게 목표였습니다. 스킬의 Judgment 규칙 중 "예약 실행 시각을 정각(예: 8시 00분)으로 잡지 않는다"를 그대로 적용해서, 처음부터 8시 정각이 아니라 8시 7분(`08:07 KST`)으로 예약해뒀습니다.

### Before — cron-job.org 추가 전

- 규칙대로 정각을 피해서 예약했는데도, 그다음 이틀(7월 20일, 7월 21일) 연속으로 자동 실행이 아예 안 일어났습니다.
- 저장소를 만든 뒤로 GitHub 자체 예약 실행(`schedule` 트리거)이 성공한 적은 **딱 1번**뿐이었습니다.
- 즉, "정각을 피하면 된다"는 규칙 하나만으로는 부족했습니다. 진짜 원인은 "몇 시로 예약했는가"가 아니라, **GitHub의 예약 실행 기능 자체가 개인 계정 저장소에서는 신뢰도가 낮다**는 것이었습니다 — 시각을 아무리 잘 잡아도 GitHub이 그 시각에 실행을 안 시켜주면 소용이 없습니다.

### After — cron-job.org 추가 후

- **cron-job.org**라는 무료 외부 서비스에 "매일 08:07(한국 시간)에 GitHub한테 '지금 실행해!'라는 신호를 대신 보내줘"라고 등록했습니다.
- 정확히는, GitHub이 제공하는 "수동으로 Run workflow 버튼을 눌렀을 때"와 똑같은 신호(`workflow_dispatch`)를 cron-job.org가 매일 정해진 시각에 인터넷으로 대신 호출해주는 방식입니다. 사람이 매일 아침 직접 버튼을 눌러주는 걸 외부 서비스가 대신 해주는 셈입니다.
- GitHub 자체 예약 실행(`schedule` 트리거)은 지우지 않고 그대로 남겨뒀습니다 — 어쩌다 스스로 도는 날은 보너스이고, 혹시 두 가지가 겹쳐서 동시에 실행돼도 안전하게 처리되도록(`concurrency` 설정) 이미 되어 있기 때문입니다.
- 결과: 이후로는 매일 안정적으로 자동 갱신되었습니다.

### 이 경험이 스킬 문서에 어떻게 남았나

이건 단순한 참고 사례가 아니라, 이번 실습에서 다시 확인해본 **SKILL.md 본문에 이미 적혀 있던 문장의 실제 출처**입니다.

- Failure repair의 "예약 실행이 그 회차만 건너뛰어짐" 항목에 있는 "분을 옮겨도 며칠씩 안 도는 경우가 실제로 있었다"는 문장이 바로 이 사건을 가리킵니다. 이 문장 덕분에, 다음에 똑같은 문제를 겪는 사람은 "정각만 피하면 되겠지"라는 잘못된 결론에서 멈추지 않고 바로 외부 스케줄러 연결로 넘어갈 수 있습니다.
- `references/github-setup.md`에 "6. 외부 스케줄러로 예약 실행 안정화"라는 상세 절차가 본문과 분리되어 있는 이유도 이 사건 때문입니다. 이 절차는 매번 필요한 게 아니라 "예약 실행이 안 돌 때만" 필요하므로, 6번 항목에서 설명한 분리 신호(③ 매번 필요하지 않은 내용은 항상 로드하지 않는다)가 실제로 들어맞는 사례입니다.

정리하면: 이번 관찰은 "AI가 스킬 문서를 잘 따라 하는가"를 새로 시험한 게 아니라, **스킬 문서 안의 Judgment 규칙과 Failure repair 조치, 그리고 파일 분리 판단이 전부 실제 사고 하나로부터 나왔고, 그 조치가 실제로 문제를 해결했다는 것을 다시 확인**한 것입니다.

## 6. 파일을 나눴나요? (분리 판단)

이 스킬에는 이미 본문과 분리된 파일 2종류가 있었습니다. 이번에 그게 "정말 나눌 이유가 있는지" 다시 점검했습니다.

| 분리된 파일 | 나눈 채로 둔 이유 (쉬운 설명) |
|---|---|
| `references/github-setup.md` (GitHub 배포 상세 가이드, 108줄) | GitHub에 저장소를 만들고 배포하는 건 프로젝트당 딱 한 번만 하는 초기 설정입니다. 스킬이 실행될 때마다 매번 이 상세 가이드를 다 읽을 필요가 없으니, "그 단계에 실제로 도달했을 때만" 열어보게 떼어뒀습니다. |
| `assets/templates/*.py`, `update.yml` (코드 템플릿) | 이건 설명 글이 아니라 실제로 복사해서 쓰는 코드 원본입니다. 판단·순서를 설명하는 본문 목적과 성격이 다르고, 역시 "그 코드를 쓰는 단계에서만" 필요합니다. |
| SKILL.md 본문 자체 (97줄) | **나누지 않았습니다.** 500줄에 한참 못 미치고(약 1/5 수준), 특정 항목만 계속 길어지는 것도 아니었습니다. 즉 "굳이 나눌 이유가 없다"는 것 자체가 이번 판단의 결론입니다. |

그리고 "떼어낸 파일을 아무 설명 없이 그냥 남겨두는 것"은 있으나 마나 하기 때문에(본문이 그 파일을 언제 읽어야 하는지 알려주지 않으면 AI가 존재 자체를 모릅니다), Steps 항목에 아래처럼 **"언제 열어봐야 하는지"를 조건문으로 명시하는 문장**을 넣어뒀습니다.

> "이 단계에 도달하면 `assets/templates/collect_template.py`를 읽고 그 구조를 기반으로 작성한다."
> "이 단계에 도달하면 `references/github-setup.md`를 읽고 그 순서를 그대로 따른다."

## 7. 최종 점검 (성공 기준 자가 확인)

Mission 02가 제시한 3가지 성공 기준에 하나씩 답합니다.

1. **description만 보고도 언제 발동할지 알 수 있는가?** → 예. 표지에 구체적인 문장 예시들("자동으로 업데이트되는 웹사이트" 등)과 "명시적 요청이 없어도 먼저 쓴다"는 문구가 들어 있습니다.
2. **문서에 적힌 Judgment·Failure repair가 실제 상황에서도 통하는가?** → 예(5번 인천대 알림 프로젝트 사례로 확인). "정각을 피한다"는 규칙만으로는 부족했던 실제 실패(이틀 연속 자동 실행 누락)가 있었고, 그 실패가 그대로 Failure repair 항목과 references/github-setup.md의 외부 스케줄러 절차로 문서에 반영되어 이후 문제를 실제로 해결했습니다. 지어낸 규칙이 아니라 실제 사고에서 나온 규칙이라는 뜻입니다.
3. **분리했다면 이유를 신호로 설명할 수 있는가? 안 했다면 그 이유도 말할 수 있는가?** → 예. 위 6번 표 참고. 기존에 나눠져 있던 두 파일은 "실행할 때마다 매번 필요한 게 아니다"라는 신호로 설명되고, 본문 자체는 "아직 나눌 만큼 길지도, 특정 항목만 비대해지지도 않았다"는 이유로 나누지 않았습니다.

## 8. 한 줄 정리

스킬 문서를 처음부터 여러 파일로 쪼개 설계하지 않고, **"표지(언제 쓰나) → 본문(판단·순서·체크리스트) → 딸린 파일(그때그때 필요한 것만)"** 순서로 한 문서에 다 담은 뒤, 실제로 시험해보고 구멍이 발견된 부분만 본문에 덧붙이는 방식이 이번 실습에서 잘 통했습니다. 파일을 더 쪼갤지 말지는 "줄 수가 늘었는가, 특정 항목만 계속 비대해지는가, 매번 안 쓰는 내용이 항상 딸려 들어오는가" 세 가지 신호로 판단하면 되고, 그 신호가 없으면 "한 파일로 충분하다"는 결론도 정답이 될 수 있습니다.
