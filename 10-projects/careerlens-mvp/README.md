## 진행 상황 업데이트 (2026-08-23, v2 실행 방법 수정 — 반드시 로컬 서버로 열 것)
- **실제 테스트에서 발견된 문제**: `file:///...careerlens-mvp-2.html`처럼 더블클릭으로 직접 열면, 콘솔에 `'file:' URLs are treated as unique security origins` 에러가 뜨면서 AI 모델 로딩이 불안정해짐(성공할 때도, 실패할 때도 있음). **크롬이 `file://`에서 열린 페이지의 ES 모듈(동적 로딩·워커)을 보안상 제한하기 때문**입니다. v1은 모듈을 안 써서 이 문제가 없었는데, v2는 transformers.js가 내부적으로 모듈 방식을 쓰다 보니 영향을 받음.
- **해결책**: v2는 반드시 로컬 웹 서버로 열어야 함. 파이썬이 설치되어 있으면:
  ```
  cd 10-projects/careerlens-mvp/src
  python -m http.server 8000
  ```
  그 다음 브라우저에서 `http://localhost:8000/careerlens-mvp-2.html`로 접속 (file:// 아님, http:// 여야 함). v1은 모듈을 안 쓰므로 기존처럼 더블클릭으로 열어도 무방함.
- 추가 안전장치: `showResults()`에 모델이 준비되지 않은 상태에서 결과가 생성되는 걸 막는 방어 코드 추가 (신뢰할 수 없는 결과 대신 안내 문구 표시).
- **✅ 확인 완료 (2026-08-23)**: `http://localhost:8000`으로 재테스트한 결과, `'file:' URLs are treated as unique security origins` 에러가 더 이상 발생하지 않음. 콘솔에 남은 항목(폰트 CDN Tracking Prevention 경고 4개, favicon.ico 404)은 AI 모델과 무관한 무해한 메시지로 확인됨(favicon 404는 `<link rel="icon" href="data:,">` 추가로 제거함). **v2는 로컬 서버로 열면 정상 작동합니다.**
- 진단을 위해 `loadModelAndEmbed()`에 `console.log` 체크포인트와 오류 배너에 "🔄 다시 시도" 버튼을 추가함.
- **🐛 버그 발견·수정 1**: 재시도 버튼을 눌렀을 때 `TypeError: Cannot set properties of null (setting 'textContent')` 발생. 원인은 최초 로딩 성공 시 로딩 배너를 `.remove()`로 DOM에서 완전히 삭제하는데, 그 안의 진행률 텍스트 요소(`#loadingDetail`)도 자식이라 같이 사라져서 재시도 시 참조가 끊긴 것. `.remove()` 대신 `.hidden = true`로 바꿔서 요소는 남기고 숨기기만 하도록 수정.
- **🐛 버그 발견·수정 2 (진짜 핵심 원인)**: 콘솔은 매번 100% 성공(`임베딩 74개 전부 계산 완료 ✅`)했는데도 화면엔 로딩 배너·에러 배너가 계속 보이는 문제가 있었음. 원인은 CSS — `.loading-banner`, `.error-banner`, `.explain-panel`에 `display: flex`를 직접 지정해뒀는데, 이게 HTML `hidden` 속성의 기본 동작(`display: none`)과 명시도가 같거나 낮아서 덮어써버림. 그래서 JS로 `hidden = true`를 아무리 설정해도 화면엔 계속 표시됐던 것. **`.loading-banner[hidden], .error-banner[hidden], .explain-panel[hidden] { display: none !important; }`** 규칙을 추가해 해결 (v1의 설명 탭도 같은 문제가 있어서 동일하게 수정함). 지금 돌이켜보면 이전 대화에서 "성공했는데 에러 배너가 안 사라진다"고 여러 번 보고된 현상이 사실 전부 이 버그 때문이었을 가능성이 높음.
- **✅ 사용자 확인**: CSS 수정 후 정상 작동 확인됨.

  2. "계층적으로 묶으면 1단계와 12단계처럼 멀리 떨어진 카드끼리도 같은 그룹에 들어갈 수 있는 거 아니야?" → 맞는 지적. 기존에 쓰던 **평균 연결(average-linkage)**은 두 그룹의 모든 카드 쌍 점수를 평균 내기 때문에, A-B 비슷, B-C 비슷하면 A-C는 안 비슷해도 사슬처럼 하나로 묶이는 "chaining" 문제가 생김.
- **수정 내용** (`src/careerlens-mvp-2.html`):
  - `buildSimilarityMap()`: min-max 정규화를 제거하고 코사인 유사도 **원값**을 그대로 사용 (`최종 점수 = 0.6×공동출현 + 0.4×코사인 원값`).
  - `clusterCards()`: **평균 연결 → 완전 연결(complete-linkage)**로 전환. 두 그룹을 합칠 기준을 "모든 쌍의 평균"이 아니라 "가장 점수가 낮은(가장 안 비슷한) 쌍"으로 삼아서, 최종 그룹 안의 **모든 카드 쌍이 기준선을 반드시 넘는다는 것을 구조적으로 보장**하도록 바꿈.
  - `buildRecommendation()`에 `weakestPair`(그룹 내 가장 낮은 점수 쌍) 추가, 결과 화면에 "⚖️ 이 그룹의 가장 약한 연결고리(그래도 기준선은 넘었어요)"로 표시 — "완전 연결" 보장을 사용자가 직접 눈으로 확인할 수 있게 함.
  - 설명 탭(6곳)도 새 방식(정규화 없음 + 완전 연결)에 맞게 문구 전면 수정.
- **트레이드오프**: 완전 연결은 엄격해서 사슬처럼 묶이는 문제는 막지만, 카드 하나가 나머지와 조금만 안 맞아도 그룹이 더 잘게 쪼개질 수 있음 — `MERGE_THRESHOLD`(0.2) 재튜닝이 더 중요해짐.
- **⚠️ 아직 실제 브라우저 재검증 전**: 이 수정 이후 사용자가 다시 테스트하지 않음. 다음 세션에서 로컬 서버로 열어 재확인 필요.

- **수정 1 — 도메인 혼합 근거를 구체적 카드 쌍으로 제시**: `src/careerlens-mvp-4.html`의 `buildRecommendation()`에서, 도메인이 2개 이상 섞인 묶음일 때 그 안에서 **서로 다른 도메인끼리 코사인 유사도가 가장 높았던 실제 카드 쌍**을 찾아 "구체적으로는 'A'(도메인1)와 'B'(도메인2)가 의미상 가장 비슷했어요(유사도 0.60)"처럼 문장에 추가. AI가 "공통 주제"를 직접 요약해주는 게 아니라(임베딩은 그런 설명을 못 함, 설명 탭에 이미 명시된 한계), 실제 계산값 중 근거가 되는 쌍을 그대로 보여줘서 사용자가 공통점을 스스로 짐작할 수 있게 하는 방식 — 없는 능력을 있는 것처럼 꾸미지 않음.
- **수정 2 — `DOMAIN_RECOMMEND` 9개 전부 쉬운 말 우선으로 통일**: 기존엔 일부만 괄호 설명이 붙어 있어 화면에 "광고테크·소상공인 마케팅 + 핀테크·금융 (은행...)"처럼 한쪽만 풀이되는 비대칭이 있었음. 9개 전부 "쉬운 말 (원래 도메인명)" 형태로 통일 — 예: "B2B AI·SaaS" → "기업을 상대로 파는 AI 서비스 (B2B AI·SaaS)".
- **검증**: 사용자가 실제로 받았던 결과(광고테크·소상공인마케팅+핀테크·금융, B2B AI·SaaS+이커머스·물류, 교육·에듀테크 단독)와 동일한 카드 조합(id 59+5, 24+41, 65+69)으로 Playwright 재현 — 새 문장과 쉬운 말 라벨이 의도대로 출력됨을 확인, 콘솔 에러 0건. `node --check` 문법 확인·HTML 태그 균형 확인도 통과.

## 진행 상황 업데이트 (2026-09-02, 도메인 카드 개수 편향 보정 — "선택 개수" → "선택 비율")
- **문제 제기**: 도메인 9개가 바텀업으로 만들어지다 보니 카드 개수가 도메인마다 다름(핀테크·금융 13개 ~ 미디어·저널리즘/콘텐츠·게임테크 4개). "주요 추천" 판정을 선택한 카드 **개수**로만 하면, 카드가 원래 많은 도메인이 학생의 실제 관심과 무관하게 더 자주 주요 추천이 되는 편향이 생길 수 있다는 지적.
- **근본 원인**: 계산 로직이 아니라 **수집 단계의 편향**(18건이 도메인별 균등 표본이 아니라 우연히 이 비율로 모임). 근본 해결은 향후 수집 시 도메인별 최소 개수를 맞추는 쿼터 샘플링이지만 시간이 걸리는 별도 작업.
- **즉시 적용한 보정** (`src/careerlens-mvp-4.html`):
  - `DOMAIN_DECK_SIZE`: CARDS 77개에서 도메인별 전체 카드 수를 미리 집계.
  - `domainSelectionRatio(members)`: 묶음의 대표 도메인(들) 카드 총량 대비 이번에 선택된 카드 수 비율을 계산.
  - `splitPrimaryAndReference()`: 기존엔 `가장 큰 묶음의 카드 개수 × PRIMARY_RATIO`를 절대 개수 기준(cutoff)으로 썼는데, 이제 `가장 높은 선택 비율 × PRIMARY_RATIO`를 비율 기준(cutoff)으로 바꿈. `PRIMARY_MIN_SIZE`(절대 최소 2개)는 그대로 유지.
  - 결과 화면 "계산 과정 보기"에 "📊 카드 선택 비율(주요·참고 판정 기준)" 줄을 추가해 실제 계산값을 투명하게 공개.
- **검증(Playwright)**: 핀테크·금융 6장(13개 중 46%, 절대 개수 많음) + 미디어·저널리즘 2장(4개 중 50%, 절대 개수 적음) 조합 테스트 — 예전 로직이면 미디어(2개 < 최대 개수 6개의 50%=3개)가 참고용으로 밀렸을 상황인데, 새 로직에서는 비율(50%>46%)이 더 높아 **두 묶음 모두 주요 추천**으로 정상 승격됨을 확인. 계산 과정 보기의 비율 문구("핀테크·금융 카드 13개 중 6개 선택(46%)", "미디어·저널리즘 카드 4개 중 2개 선택(50%)")도 정확히 표시. 콘솔 에러 0건, `node --check`·HTML 태그 균형 확인 통과.
- **설명 탭 반영**: 처음엔 "이 프로그램은 어떻게 작동하나요? → 작동 원리 설명"에 기존 보라색 accent 박스와 구분되는 **주황색 박스**(`.explain-box.bias-note`, warn 색상 재사용)로 추가했다가, 사용자 요청으로 **"도메인은 어떻게 정했나요?" 탭 → "도메인 기준을 정한 방법" 섹션 맨 끝**(바텀업 설명·결정 표 다음, "도메인 후보 9개" 표 이전)으로 옮김 — 이 문제 자체가 도메인 구성 방식(바텀업이라 카드 개수가 불균등해짐)에서 비롯된 것이라 도메인 탭에 두는 게 더 맞는 위치. Playwright로 작동 원리 탭에는 더 이상 없고 도메인 탭에만 있음을 확인.
