## 1. 이 프로그램은 한 줄로 뭘 하나요?

커리어 방향이 정해지지 않은 학생에게 **"하는 일" 문장 77개(업무카드)**를 보여주고, 학생이 끌리는 카드를 여러 개 고르면, AI가 그 카드들의 **의미가 서로 얼마나 비슷한지**를 계산해서 자동으로 묶고 **어떤 산업 도메인에 관심이 있는지**를 추천해줍니다.

전체 흐름은 4단계입니다.

1. **카드 준비**: 업무카드 77개 + 각 카드에 미리 붙여둔 산업 도메인(9개) 태그
2. **유사도 계산**: 학생이 고른 카드끼리 AI 의미 분석 모델로 코사인 유사도를 계산
3. **자동 그룹핑**: 유사도가 기준선 이상인 카드끼리 묶음(계층적 군집화)
4. **추천 + 근거 설명**: 묶음 안에서 가장 많은 도메인을 추천하고, 왜 그렇게 묶였는지 실제 계산값으로 설명

외부 서버·API 호출 없이 **브라우저 안에서 전부 계산**됩니다. 단, 처음 실행할 때 AI 모델 파일을 인터넷에서 내려받아야 하므로 최초 1회는 인터넷 연결이 필요합니다.

## 2. 실행 방법 (중요 — 더블클릭하면 안 됩니다)

```
cd 10-projects/careerlens-mvp/src
python -m http.server 8000
```

그다음 브라우저에서 `http://localhost:8000/careerlens-mvp-4.html`로 접속합니다.

**왜 더블클릭(`file://`)으로 열면 안 되나요?**
AI 모델을 불러오는 라이브러리(`transformers.js`)가 내부적으로 "ES 모듈"이라는 방식을 쓰는데, 크롬은 보안상 `file://` 주소에서 열린 페이지의 모듈 로딩·백그라운드 작업(워커)을 제한합니다. 그래서 `file://`로 열면 모델 로딩이 실패하거나 될 때도 있고 안 될 때도 있는 식으로 불안정해집니다. 반드시 `http://`로 열어야 합니다.

### 3.3 도메인은 어떤 기준으로 9개로 정했나요?

**직무가 아니라 산업입니다.** 데이터분석·데이터사이언스·데이터엔지니어링 같은 "무슨 기술을 쓰는가"(직무)가 아니라, 핀테크·헬스케어·이커머스처럼 "어느 산업에서 일하는가"(도메인)를 기준으로 삼았습니다. 원래 이 프로젝트의 목표가 "학생이 관심 산업을 찾는 것"이었는데, v1~v3까지는 실수로 직무 카테고리를 쓰고 있었다는 게 뒤늦게 발견되어 v4에서 바꿨습니다.

도메인 9개를 정한 3가지 결정과 이유:

| 결정 | 선택 | 이유 |
|---|---|---|
| 표준산업분류(KSIC)를 그대로 쓸 것인가 | 아니요 — **바텀업**(실제 사례를 먼저 보고 공통점을 묶어 올라감)으로 직접 구성 | KSIC 대분류만 21개라 카테고리가 너무 많고, 이 프로젝트 목적과 안 맞는 항목이 많이 섞임 |

### 3.4 카드 문구는 어떤 원칙으로 썼나요?

카드 문구는 "**데이터로 어떻게 하는가**"(SQL·모델링·파이프라인 같은 기법 이야기)는 줄이고, "**어떤 도메인의 어떤 목표·문제를 위한 일인가**"가 드러나도록 다시 썼습니다. 데이터과학과 학생이면 기법 자체는 이미 배우는 베이스라고 보고, 정작 구분이 필요한 "어느 산업에 끌리는가" 쪽을 카드 문구에 되살린 것입니다.

예시:

| 이전 (v1~v3, 직무 중심) | 지금 (v4, 도메인 중심) |
|---|---|
| "안정적 데이터 흐름 지원" — 신뢰할 수 있는 안정적인 데이터 파이프라인 지원 | "주문처리 데이터 흐름 지원" — 이커머스 **주문·배송 처리가 끊기지 않도록** 안정적인 데이터 흐름을 지원하는 일 |

**주의할 점 — 편견 제거와 도메인 정보는 다른 축입니다.** v1~v3 카드를 만들 때 "회사명·제품명 등 편견 요소 제거"라는 원칙을 세웠는데, 이 작업이 산업 맥락까지 함께 지워버린 게 문제였습니다(예: "의료 데이터 기반 anomaly detection" → "이상 거래·이상 신호 자동 탐지"로 "의료"가 통째로 사라짐). v4는 **회사명·제품명은 계속 가리되, 산업 맥락은 남기는 방식**으로 다시 썼습니다.

새 카드를 추가할 때도 이 원칙(회사명은 가리기, 산업 맥락은 남기기)을 지켜야 v4의 도메인 축이 계속 의미가 있습니다.

### 3.6 공고 문장에서 업무카드를 뽑아낸 기준·방법

카드는 자동 추출이 아니라, 18건 공고의 `work_summary`(주요업무) 원문을 **사람이 한 문장씩 읽으며 직접 잘라내고 다시 쓰는** 방식으로 만들었습니다. 원칙은 3가지입니다.

1. **편견 요소 제거** — 회사명·제품명 등 특정 기업을 특정하는 단어를 일반화된 표현으로 바꿈.
   - 예: "동네 가게" → "소상공인·지역 비즈니스", "머스타드TV 도입" → "자사 서비스·제품 도입"
2. **여러 업무가 묶인 문장은 개별 카드로 분리** — 원문 한 문장에 업무가 여러 개 나열돼 있으면(예: "①~하고 ②~하고 ③~한다"), 카드 하나에 업무 하나만 담기도록 쪼갬.
3. **사실상 같은 내용을 가리키는 카드만 병합** — 여러 공고에 걸쳐 표현이 거의 같은 카드는 하나로 합침. 실제로는 18건·74개 카드 중 이 기준에 해당한 건 **딱 3쌍뿐**이고, 나머지는 전부 공고 1건에서만 나온 표현이었음(→ "같이 나온 횟수"로 유사도를 계산하는 공동출현 방식이 신호가 희박했던 직접적인 이유, 5.3절 참고).

**문구 형식**: 모든 카드는 "**제목: 명사형 설명**" 형태로 통일했습니다. 예: "개인화 추천: 사용자 맞춤형 콘텐츠 및 상품 추천".

**참고 키워드(`kw` 필드)는 어떻게 붙였나**: 알고리즘이 아니라 사람이 각 카드 문장을 읽고 손으로 골랐습니다. 원칙은 ① 문장에서 진짜 구분되는 핵심 개념 2~3개만 뽑고 ② **같은 개념이면 카드가 달라도 똑같은 글자를 재사용**(예: "시각화"라는 단어를 여러 카드에 의도적으로 반복)하는 것입니다. `kw`는 실제 그룹핑 계산(5장)에는 쓰이지 않고 화면 표시·참고용입니다.

**결과**: 이 과정을 거쳐 18건 공고 → **74개 카드 초안**이 나왔고(2026-08-22~23), 이후 2026-09-02에 "직무 기법 중심 → 산업 도메인 중심"으로 문구를 다시 쓰면서(3.4절) 도메인이 다른데 잘못 합쳐져 있던 카드 3쌍이 재분리되어 최종 **77개**가 됐습니다.

## 4. 외부 AI 의미 분석 모델

### 4.1 무슨 모델을 쓰나요?
- 모델 이름: **`Xenova/paraphrase-multilingual-MiniLM-L12-v2`** (원본: Hugging Face의 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`)
- 코드 상 위치: `MODEL_NAME` 상수 (약 884번째 줄)
- 역할: 문장을 숫자 384개짜리 목록(임베딩 벡터)으로 바꿔주는 **다국어 문장 임베딩 모델**. "다국어"라 한국어 카드 문구도 뜻을 이해할 수 있습니다.

### 4.2 어떻게 브라우저 안에서 AI 모델이 돌아가나요?
- **`transformers.js`**라는 라이브러리를 씁니다. 보통 이런 AI 모델은 파이썬 서버에서 돌리는 게 일반적인데, 이 라이브러리는 모델을 브라우저가 이해할 수 있는 형태로 변환해서 **사용자 컴퓨터(브라우저) 안에서 직접** 계산하게 해줍니다. 그래서 외부 API 호출 비용·서버 운영이 전혀 필요 없습니다.
- 코드 최상단에서 CDN으로 라이브러리를 불러옵니다:
  ```js
  import { pipeline, env } from 'https://cdn.jsdelivr.net/npm/@xenova/transformers@2.17.2';
  ```
  버전(`@2.17.2`)을 **고정**해뒀습니다. 이 URL이 나중에 로드되지 않으면(CDN에서 옛 버전을 내렸을 경우), [npmjs.com/package/@xenova/transformers](https://www.npmjs.com/package/@xenova/transformers)에서 최신 버전 번호를 확인해 URL의 `@2.17.2` 부분을 교체하면 됩니다.
- 최초 실행 시 모델 파일을 CDN에서 내려받는 데 **약 30초 정도** 걸립니다(실측: 77개 카드 임베딩 계산까지 약 29초). 두 번째 실행부터는 브라우저 캐시 덕분에 더 빠를 수 있습니다.

### 4.3 모델은 정확히 어디까지 하고, 어디부터는 우리 코드가 하나요?

| 단계 | 누가 하나 | 하는 일 |
|---|---|---|
| ① 문장 → 384차원 좌표로 변환 | **AI 모델** | 카드 문구 하나하나를 숫자 384개짜리 좌표로 바꿈. 카드마다 독립적으로, 페이지 로딩 시 77개 전부 미리 한 번만 계산해둠 |
| ② 두 좌표가 얼마나 가까운지 계산 (코사인 유사도) | **우리가 짠 코드** | 이미 계산된 두 좌표를 받아서 곱셈·덧셈만으로 계산. 모델은 이 계산에 전혀 관여하지 않음 |

즉 "AI가 코사인 유사도까지 계산해준다"는 건 오해입니다. **AI는 문장을 좌표로 바꾸는 것까지만** 하고, 그 좌표끼리 얼마나 가까운지 재는 건 순수한 산수(다음 절 참고)입니다.

## 5. 코사인 유사도 계산 기준

### 5.1 코사인 유사도란
두 문장을 좌표(임베딩)로 바꾸면, 두 좌표가 원점에서 볼 때 얼마나 비슷한 "방향"을 가리키는지 계산할 수 있습니다. 완전히 같은 방향이면 1, 완전히 무관하면 0에 가깝습니다. **"숫자가 얼마나 큰가"가 아니라 "방향이 얼마나 일치하는가"**만 보는 계산이라 이름이 "코사인"(각도) 유사도입니다.

### 5.2 실제 계산 코드
```js
function cosineSim(vecA, vecB) {
  let dot = 0;
  for (let i = 0; i < vecA.length; i++) dot += vecA[i] * vecB[i];
  return dot; // normalize:true로 이미 단위벡터라 내적 = 코사인 유사도
}
```
모델에서 좌표를 뽑을 때 이미 길이 1로 정규화(`normalize: true`)해두기 때문에, 두 벡터를 곱해서 더하기만 해도(내적) 바로 코사인 유사도가 나옵니다. 별도의 나눗셈(벡터 길이로 나누는 과정)이 필요 없습니다.

### 5.3 점수 = 코사인 유사도 그 자체 (다른 신호를 섞지 않음)
```
점수 = 코사인 유사도 원값(약 -1~1, 실제로는 대부분 0~1) — 그 외에는 아무것도 섞지 않음
```
- v4는 v3와 동일하게, **"같은 채용공고 출처인가"(공동출현) 같은 다른 신호를 전혀 섞지 않습니다.** 그래서 "AI 의미 유사도(코사인 유사도)"와 "그룹을 묶을지 판단하는 점수"가 완전히 같은 값입니다.
- 참고로 v2에서는 `점수 = 공동출현×0.6 + 코사인×0.4`처럼 두 신호를 섞었는데, 이 방식은 "의미 유사도는 높은데 왜 점수는 낮지?" 같은 혼란을 일으켰습니다. v3부터는 공동출현 개념 자체를 없애서 이 문제를 구조적으로 없앴습니다(이유: 카드 74개 중 공동출현 쌍이 딱 3쌍뿐이라 신호가 너무 희박했음).

### 5.4 기준선(threshold): 0.5
```js
const MERGE_THRESHOLD = 0.5;
```
- 코사인 유사도가 **0.5 이상**이면 두 카드(또는 두 묶음)를 합치고, 미만이면 합치지 않습니다.
- **⚠️ 이 값은 아직 검증되지 않은 출발값입니다.** v3에서 쓰던 값을 그대로 가져왔을 뿐이고, v3의 0.5도 "v2에서 공동출현이 없는 쌍이 통과하려면 코사인 유사도가 사실상 0.5 이상이어야 했다"는 관찰(`0.4 × 0.5 = 0.2`, v2의 통과 기준선)에서 역산한 값입니다. v4는 카드 문구 자체를 완전히 다시 썼기 때문에 임베딩 분포도 달라졌을 수 있어, **여러 카드 조합으로 재테스트하며 조정이 필요**합니다. (다음 세션에서 가장 먼저 손볼 만한 부분입니다.)

## 6. 카드를 그룹으로 묶는 방법 (군집화)

### 6.1 계층적 응집 군집화 + 완전 연결(complete-linkage)
- 처음엔 카드 하나하나가 자기 자신만의 묶음입니다. 그중 코사인 유사도가 가장 높은 두 묶음을 계속 합쳐나갑니다(계층적 응집).
- 이때 "두 묶음을 합칠 기준"으로 **완전 연결(complete-linkage)** 방식을 씁니다: 두 묶음의 모든 카드 쌍 중 **가장 안 닮은 쌍(최소 유사도)**이 기준선(0.5) 이상이어야 합칩니다.
- (참고로 평균 연결(average-linkage) 방식을 v2 초기에 썼다가, "A-B 비슷, B-C 비슷하면 A-C는 안 비슷해도 사슬처럼 하나로 묶이는" chaining 문제가 발견되어 완전 연결로 바꿨습니다.)
- 결과: 최종 묶음 안의 **모든 카드 쌍이 반드시 기준선을 넘는다는 것이 구조적으로 보장**됩니다. 대신 엄격해서, 카드 하나가 나머지와 조금만 안 맞아도 그룹이 쉽게 쪼개질 수 있습니다.

### 6.2 같은 도메인 묶음은 화면에서 통합 (`mergeSameDomainClusters`)
- 완전 연결이 너무 엄격하다 보니, 실제로는 같은 도메인 카드들인데도 세부 유사도 차이로 여러 개의 작은 묶음으로 쪼개지는 경우가 있습니다.
- 이때 계산 자체(완전 연결 로직)는 그대로 두고, **최종적으로 추천할 도메인이 같은 묶음끼리는 화면에는 하나로 합쳐서** 보여줍니다.
- 정직성을 지키기 위해, 실제로는 하위 묶음이 여러 개였다는 사실을 숨기지 않고 "🔗 하위 묶음 N개가 합쳐졌어요"라고 안내하며, 이 경우 "가장 약한 연결고리" 점수가 기준선보다 낮을 수도 있다는 걸 문구로 구분해 보여줍니다.

## 7. "주요 추천" vs "참고용" 판정 기준

### 7.1 기본 조건
```js
const PRIMARY_MIN_SIZE = 2;   // 카드 2개 이상
const PRIMARY_RATIO = 0.5;    // 가장 높은 "선택 비율"의 50% 이상
```
어떤 묶음이 ① 카드 2개 이상이고, ② 아래 7.2절의 "선택 비율" 기준으로 가장 높은 묶음의 50% 이상이어야 "주요 추천"으로 화면 상단에 표시됩니다. 둘 중 하나라도 못 만족하면 결과 화면 하단에 "참고용"으로만 작게 표시됩니다.

### 7.2 왜 "선택 개수"가 아니라 "선택 비율"을 쓰나요?
- 도메인마다 원래 카드 개수가 다릅니다(핀테크·금융 13개 ~ 미디어·저널리즘 4개, 3.2절 표 참고). 만약 "주요 추천"을 **선택한 카드 개수**로만 판정하면, 카드가 원래 많은 도메인일수록 뽑힐 기회도 많아져서 학생의 실제 관심과 무관하게 자주 "주요 추천"이 되는 편향이 생깁니다.
- 근본 원인은 계산 방식이 아니라 **수집 단계의 편향**입니다(공고 18건이 도메인별로 똑같이 모인 게 아니라 우연히 이 비율로 모임). 가장 정직한 해결책은 앞으로 공고를 모을 때 도메인별 최소 개수를 맞추는 것(쿼터 샘플링)이지만, 이건 별도의 데이터 수집 작업입니다.
- **지금 적용한 즉시 보정**: 판정 기준을 "선택한 카드 개수"에서 **"선택 비율"**(그 도메인 카드 중 몇 %를 골랐는가)로 바꿨습니다.
  - `DOMAIN_DECK_SIZE`: 도메인별 전체 카드 수를 미리 집계
  - `domainSelectionRatio(members)`: 묶음의 대표 도메인 카드 총량 대비, 이번에 선택된 카드 수 비율을 계산
  - 예: 핀테크·금융(13개 중 6개=46%)과 미디어·저널리즘(4개 중 2개=50%)을 비교하면, 개수는 핀테크·금융이 많아도 비율은 미디어·저널리즘이 더 높아서 더 유리하게 판정됩니다.
- 결과 화면의 "계산 과정 보기"에 "📊 카드 선택 비율" 줄로 실제 계산값을 투명하게 공개합니다.

## 8. 결과 화면에서 근거를 어떻게 보여주나요?

- **도메인 다수결**: 묶음 안에서 가장 많이 나온 도메인을 추천합니다.
- **평균 의미 유사도**: 묶음 안 카드 쌍들의 평균 코사인 유사도를 "얼마나 확신하는 추천인지"의 근거로 함께 보여줍니다.
- **도메인이 섞인 경우**: 여러 도메인이 하나로 묶였을 때는, 그 안에서 **서로 다른 도메인끼리 코사인 유사도가 가장 높았던 실제 카드 쌍**을 찾아 "구체적으로는 'A'(도메인1)와 'B'(도메인2)가 의미상 가장 비슷했어요(유사도 0.60)"처럼 보여줍니다. AI가 "왜 비슷한지" 자체를 설명해주는 능력은 없으므로(임베딩 모델의 한계), 대신 실제 계산값 중 근거가 되는 쌍을 그대로 보여줘서 사용자가 공통점을 스스로 짐작하게 하는 방식입니다 — 없는 능력을 있는 것처럼 꾸미지 않는다는 원칙입니다.
- **가장 약한 연결고리**: 그 묶음에서 코사인 유사도가 가장 낮았던 쌍을 "그래도 기준선은 넘었어요"(완전 연결이 실제로 보장한 경우) 또는 "기준선보다 낮지만 같은 도메인 추천이라 함께 묶었어요"(6.2절의 화면 통합으로 합쳐진 경우) 문구로 구분해 보여줍니다.
