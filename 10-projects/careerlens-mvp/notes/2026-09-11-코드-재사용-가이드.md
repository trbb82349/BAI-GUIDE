# CareerLens v4 — 코드 재사용 가이드 (통합 프로그램에 그대로 갖다 쓰는 경우)

이 문서는 `src/careerlens-mvp-4.html`의 **JS 코드를 그대로 재사용**해서 다른 통합 프로그램에 합칠 때 필요한 코드 수준 정보를 정리한 것입니다. "왜 이렇게 설계했는가"는 [2026-09-11-프로그램-구성-설명.md](2026-09-11-프로그램-구성-설명.md)에 이미 있으므로, 여기서는 **정확히 어떤 함수를 어떻게 가져다 쓸 수 있는지**만 다룹니다.

(같은 로직을 다른 언어·스택으로 새로 구현하는 경우를 위한 "알고리즘 스펙" 버전은 [2026-09-11-알고리즘-스펙-재구현용.md](2026-09-11-알고리즘-스펙-재구현용.md)에 있습니다.)

---

## 1. 지금 코드의 형태

- 파일 하나(`careerlens-mvp-4.html`) 안에 HTML + CSS + JS가 전부 들어있는 **단일 파일 구조**입니다. 빌드 스텝(webpack, npm install 등)이 없습니다.
- JS는 `<script type="module">` 안에 있습니다 — **ES 모듈**이라 `import` 문법을 씁니다. 그래서 `file://`로 직접 열면 동작하지 않고, 반드시 `http://`(로컬 서버든 실제 배포든)로 열어야 합니다. 통합 후에도 이 제약은 그대로 유지됩니다.
- 외부 의존성은 딱 하나입니다:
  ```js
  import { pipeline, env } from 'https://cdn.jsdelivr.net/npm/@xenova/transformers@2.17.2';
  ```
  CDN에서 직접 불러오며, 버전(`@2.17.2`)이 고정되어 있습니다. 통합 프로그램이 자체 번들러(webpack/vite 등)를 쓴다면, `npm install @xenova/transformers@2.17.2` 후 일반 import로 바꿀 수 있습니다(동작은 동일).

## 2. 함수 분류 — "그대로 재사용 가능" vs "DOM과 얽혀 있어 재작성 필요"

코드가 UI 렌더링 함수와 순수 계산 함수로 섞여 있어서, 통합 시 어떤 함수를 그대로 복사해 쓸 수 있는지 구분이 필요합니다.

### 2.1 순수 로직 함수 (DOM 의존 없음 — 그대로 복사해서 재사용 가능)

| 함수 | 입력 | 출력 | 역할 |
|---|---|---|---|
| `pairKey(id1, id2)` | 카드 id 2개 | 문자열(`"3_7"` 형태) | 두 카드 쌍을 맵의 키로 쓰기 위한 정규화(작은 id가 항상 앞) |
| `cosineSim(vecA, vecB)` | 임베딩 벡터 2개(숫자 배열) | 숫자(코사인 유사도) | 두 벡터의 내적 계산 (이미 정규화된 벡터라 내적 = 코사인 유사도) |
| `buildSimilarityMap(cards)` | 카드 객체 배열(`embedding` 필드 포함) | `{ map, min, max }` — `map`은 `pairKey → {score, cos}` | 선택된 카드 전체 쌍의 코사인 유사도를 미리 계산 |
| `clusterCards(cards, simMap)` | 카드 배열, `buildSimilarityMap`의 `map` | `{ clusters, mergeLog }` | 완전 연결(complete-linkage) 계층적 군집화 |
| `domainCounts(members)` | 카드 배열 | `[[도메인, 개수], ...]` (개수 내림차순) | 묶음 안 도메인 분포 집계 |
| `domainSelectionRatio(members)` | 카드 배열 | `{ ratio, pct, details }` | 도메인별 카드 개수 편차를 보정한 "선택 비율" 계산 (`DOMAIN_DECK_SIZE` 상수에 의존) |
| `mergeSameDomainClusters(clusters)` | `clusterCards`의 `clusters` | 그룹 배열(`{members, subClusters}`) | 같은 도메인으로 판정되는 하위 묶음을 하나로 통합 |
| `splitPrimaryAndReference(clusters)` | 그룹 배열 | `{ primary, reference }` | "주요 추천" vs "참고용" 분류 (`PRIMARY_MIN_SIZE`, `PRIMARY_RATIO` 상수에 의존) |
| `describeLabels(labels)` | 카드 라벨 문자열 배열 | 문자열 | 라벨 목록을 사람이 읽기 좋은 한국어 문구로 변환 (한국어 하드코딩, 2.3절 참고) |
| `buildRecommendation(cluster, simMap, mergeLog)` | 그룹 하나, simMap, mergeLog | 추천 결과 객체(`fieldLabel, why, members, steps, topPairs, weakestPair, avgCos, subCount, ratioText`) | 그룹 하나를 최종 추천 문장·근거로 변환 |

이 함수들은 `document.*` 호출이 전혀 없어서, 브라우저든 Node.js든(임베딩 벡터만 어디선가 구해서 넘겨주면) 그대로 옮겨 써도 동작합니다.

### 2.2 DOM에 강하게 결합된 함수 (그대로 재사용 불가 — 통합 프로그램의 UI 방식에 맞게 다시 짜야 함)

| 함수 | 하는 일 | 통합 시 참고사항 |
|---|---|---|
| `renderGrid()` | 카드 77개를 그리드로 렌더링, 클릭 이벤트 등록 | 카드 선택 UI를 통합 프로그램 컴포넌트로 새로 만들어야 함. `DISPLAY_ORDER`(셔플된 id 순서)와 `selected`(Set) 상태 유지 로직은 참고 가능 |
| `updateBar()` | 하단 바의 선택 개수·버튼 활성화 텍스트 갱신 | UI 프레임워크의 상태 관리로 대체 |
| `loadModelAndEmbed()` | 모델 로딩 + 로딩 배너 조작 + `CARDS[i].embedding`에 벡터를 **직접 채워 넣음(부작용)** | **주의**: 이 함수가 전역 `CARDS` 배열을 mutate합니다. 통합 시에는 "모델 로딩·임베딩 계산" 부분만 떼어내고, 배너 조작(`loadingBanner`, `errorBanner` DOM 접근)은 제거한 뒤 그 결과(카드별 벡터)를 통합 프로그램의 상태 관리 방식으로 저장하는 게 안전합니다 |
| `showResults()` | 순수 로직 함수들을 호출한 뒤 결과 HTML을 직접 그림(`innerHTML`) | **로직 호출 순서(아래 3장)는 그대로 참고**하고, 렌더링 부분만 통합 프로그램의 컴포넌트로 교체 |
| `backToGrid()`, `switchTab()`, `switchExplainSub()`, `updateBarVisibility()` | 탭 전환, 화면 전환 | 통합 프로그램의 라우팅/탭 방식으로 대체 |
| 파일 맨 아래 "초기화" 블록(1326번째 줄~) | DOM 요소에 이벤트 리스너 등록, `loadModelAndEmbed()` 최초 호출 | 통합 프로그램의 컴포넌트 마운트 시점 로직으로 대체 |

### 2.3 주의: 결과 문구(`why`, `ratioText` 등)에 한국어 문장이 하드코딩되어 있음
`buildRecommendation()`은 순수 계산뿐 아니라 **사용자에게 보여줄 한국어 설명 문장까지 함께 만들어서 반환**합니다(예: `"고르신 카드 중 5개가 모두 핀테크·금융 도메인이었고..."`). 통합 프로그램이 이 문구를 그대로 써도 되는지, 자체 톤앤매너로 다시 써야 하는지 먼저 확인이 필요합니다. 계산값(숫자)과 문구(텍스트)를 분리하고 싶다면, `buildRecommendation()`을 "숫자만 반환하는 버전"과 "문구를 만드는 버전"으로 나누는 리팩터링이 필요합니다(현재는 하나로 합쳐져 있음).

## 3. 전체 실행 흐름 (통합 시 그대로 따라야 하는 호출 순서)

```js
// 1) 페이지 로딩 시 1회: 모델을 불러오고 카드 전체의 임베딩을 미리 계산
//    (CARDS[i].embedding에 저장됨 — 카드 77개, 약 29초 소요 실측)
await loadModelAndEmbed();

// 2) 사용자가 카드를 선택 (selected: Set<id>)

// 3) "추천받기" 클릭 시:
const chosenCards = [...selected].map(id => cardById[id]);
const { map: simMap, min: simMin, max: simMax } = buildSimilarityMap(chosenCards);
const { clusters: rawClusters, mergeLog } = clusterCards(chosenCards, simMap);
const clusters = mergeSameDomainClusters(rawClusters);
clusters.sort((a, b) => b.members.length - a.members.length);

const { primary, reference } = splitPrimaryAndReference(clusters);
const primaryRecs = primary.map(c => buildRecommendation(c, simMap, mergeLog));
const referenceRecs = reference.map(c => buildRecommendation(c, simMap, mergeLog));
// primaryRecs / referenceRecs를 화면에 렌더링
```
이 순서(`buildSimilarityMap` → `clusterCards` → `mergeSameDomainClusters` → `splitPrimaryAndReference` → `buildRecommendation`)를 그대로 지켜야 정확한 결과가 나옵니다. 순서를 바꾸거나 중간 단계를 생략하면 안 됩니다.

## 4. 데이터 스키마

### 4.1 카드 객체 (`CARDS` 배열의 원소)
```js
{
  id: 1,                              // number, 1~77 고유
  domain: "핀테크·금융",               // string, 9개 도메인 중 하나
  label: "펀딩 서비스 현황 진단",       // string, 카드 제목
  desc: "크라우드펀딩 서비스가...",     // string, 카드 설명
  kw: ["크라우드펀딩", "서비스진단", "개선점도출"],  // string[], 참고용 키워드 (계산에는 안 씀)
  sources: ["와디즈"],                 // string[], 원 출처 회사 (계산에는 안 씀)
  embedding: [0.021, -0.083, ...]     // number[384] — loadModelAndEmbed() 실행 후에만 존재!
}
```
`embedding` 필드는 처음부터 있는 게 아니라 `loadModelAndEmbed()`가 실행된 **이후에만** 채워집니다. 통합 시 이 시점 의존성을 놓치지 않아야 합니다(모델 로딩 전에 `cosineSim`을 호출하면 에러가 납니다).

### 4.2 그 외 참고 상수
```js
const MIN_SELECT = 4;                 // 추천 버튼이 활성화되는 최소 선택 개수
const MERGE_THRESHOLD = 0.5;          // 코사인 유사도 기준선 (재튜닝 필요 — 프로그램 구성 설명 문서 5.4절)
const PRIMARY_MIN_SIZE = 2;           // "주요 추천" 최소 카드 개수
const PRIMARY_RATIO = 0.5;            // "주요 추천" 판정 비율 기준
const MODEL_NAME = "Xenova/paraphrase-multilingual-MiniLM-L12-v2";
const DOMAIN_DECK_SIZE = { "핀테크·금융": 13, ... };  // 도메인별 전체 카드 수 (CARDS에서 자동 집계됨)
const DOMAIN_RECOMMEND = { "핀테크·금융": "은행·결제·세금처럼 돈을 다루는 서비스 (핀테크·금융)", ... };  // 추천 문구용 도메인 설명
```
이 상수들은 로직 함수들이 참조하므로, 코드를 옮길 때 **상수도 함께** 옮겨야 합니다.

### 4.3 전역 상태
```js
const selected = new Set();  // 현재 선택된 카드 id 목록
let modelReady = false;      // 임베딩 계산이 끝났는지 여부
```
통합 프로그램이 React/Vue 같은 프레임워크를 쓴다면, 이 두 값은 컴포넌트 상태(state)로 옮기는 게 자연스럽습니다.

## 5. 통합 체크리스트

- [ ] 통합 프로그램이 **브라우저(또는 웹뷰) 환경**인지 확인 — 2.1절의 순수 로직 함수는 Node.js에서도 동작하지만, `loadModelAndEmbed()`의 모델 로딩은 브라우저의 `transformers.js` 방식을 그대로 쓸지, 서버에서 임베딩을 미리 계산해 내려줄지 결정 필요
- [ ] `@xenova/transformers` 버전(`2.17.2`)을 그대로 쓸지, 통합 프로그램의 다른 의존성과 버전을 맞출지 확인
- [ ] `CARDS[i].embedding`이 비동기로 채워진다는 시점 의존성을 통합 프로그램의 상태 관리 방식에 맞게 처리
- [ ] `buildRecommendation()`이 반환하는 한국어 문구(`why`, `ratioText`)를 그대로 쓸지, 통합 프로그램 톤에 맞게 다시 쓸지 결정 (2.3절)
- [ ] `MERGE_THRESHOLD`(0.5)가 아직 검증되지 않은 값이라는 점을 통합 담당자에게 반드시 전달 (재튜닝 필요)
- [ ] 카드 데이터(`CARDS`, `output/업무카드-도메인버전-2026-09-02.csv`)를 통합 프로그램의 데이터 소스로 그대로 쓸지, 다른 데이터로 교체할지 확인 — 교체 시 4.1절 스키마(`id, domain, label, desc`)는 유지해야 기존 로직이 그대로 동작
