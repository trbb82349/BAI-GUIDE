# CareerLens v4 — 알고리즘 스펙 (다른 언어·스택으로 재구현하는 경우)

이 문서는 `src/careerlens-mvp-4.html`의 추천 로직을 **JS 코드를 가져다 쓰지 않고, 다른 언어나 프레임워크로 새로 구현**할 때 참고하는 언어 중립적 스펙입니다. 함수 이름이나 JS 문법이 아니라 **계산 공식과 알고리즘 순서 자체**에 집중합니다.

(코드를 그대로 재사용하는 경우를 위한 함수별 가이드는 [2026-09-11-코드-재사용-가이드.md](2026-09-11-코드-재사용-가이드.md)에 있습니다. "왜 이렇게 설계했는가"는 [2026-09-11-프로그램-구성-설명.md](2026-09-11-프로그램-구성-설명.md)를 참고하세요.)

---

## 0. 전체 파이프라인 (8단계)

```
[업무카드 데이터] → 1.문장 임베딩 생성 → 2.코사인 유사도 계산 → 3.유사도 맵 구축
→ 4.완전연결 계층적 군집화 → 5.같은 도메인 그룹 통합 → 6.선택 비율 계산
→ 7.주요/참고 분류 → 8.추천 결과 구성
```
1~3단계는 "카드가 서로 얼마나 비슷한가"를 재는 준비 단계, 4~7단계는 "그래서 몇 개 그룹으로 나눌 것인가"를 정하는 단계, 8단계는 "그룹마다 무엇을 추천하고 왜인지"를 만드는 단계입니다.

---

## 1. 입력 데이터 스키마 (언어 중립)

각 업무카드는 다음 필드를 가진 레코드입니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | 정수 | 1~77 고유 식별자 |
| `domain` | 문자열 | 산업 도메인 9개 중 하나 (예: "핀테크·금융") |
| `label` | 문자열 | 카드 제목 |
| `desc` | 문자열 | 카드 설명 |
| `embedding` | 실수 384개 벡터 | 2단계에서 생성 (원본 데이터에는 없음) |

원본 카드 77개는 `output/업무카드-도메인버전-2026-09-02.csv`에 있습니다(컬럼: `id, domain, label, desc, kw, sources`). `kw`·`sources`는 참고용 표시 데이터일 뿐 계산에는 쓰이지 않으므로 재구현 시 없어도 됩니다.

## 2. 1단계 — 문장 임베딩 생성

- **모델**: 다국어 문장 임베딩 모델 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (원본 JS 구현은 이 모델의 변환본인 `Xenova/paraphrase-multilingual-MiniLM-L12-v2`를 브라우저에서 실행).
- **다른 언어 스택에서 대체하는 법**: 같은 모델을 Python `sentence-transformers` 라이브러리로 그대로 불러올 수 있습니다.
  ```python
  from sentence_transformers import SentenceTransformer
  model = SentenceTransformer("sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")
  vec = model.encode(f"{label}: {desc}", normalize_embeddings=True)
  ```
- **입력 텍스트 형식**: 반드시 `"{label}: {desc}"` 형태(제목 + 콜론 + 설명)로 합쳐서 모델에 넣습니다. 제목만 넣거나 설명만 넣으면 원본과 다른 벡터가 나옵니다.
- **풀링(pooling) 방식**: `mean`(토큰별 벡터의 평균). 다른 풀링 방식(예: CLS 토큰만 사용)을 쓰면 벡터 값이 달라집니다.
- **정규화(normalize)**: 반드시 `True`(벡터 길이를 1로 정규화). 이 조건이 성립해야 3단계의 코사인 유사도 계산이 "내적만으로" 단순화됩니다. 정규화하지 않는 라이브러리를 쓴다면 3단계 공식에 길이로 나누는 과정을 반드시 추가해야 합니다.
- **다른 임베딩 모델로 바꾸는 경우**: 모델을 바꾸면 벡터의 절대적인 값 분포가 달라지므로, 5단계 이후에 쓰는 기준선 `MERGE_THRESHOLD = 0.5`는 더 이상 유효하지 않습니다. 새 모델로 다시 실험해서 기준선을 다시 잡아야 합니다.

## 3. 2단계 — 코사인 유사도 계산

두 벡터 `A`, `B`가 이미 길이 1로 정규화되어 있다는 전제하에:

```
cosine_similarity(A, B) = Σ(A[i] × B[i])   for i = 0..383   (내적, dot product)
```

(정규화되지 않은 벡터라면 일반식 `Σ(A[i]×B[i]) / (‖A‖ × ‖B‖)`을 써야 합니다.)

결과값 범위는 이론상 -1~1이지만, 실제 문장 임베딩끼리는 대부분 0~1 사이 값이 나옵니다.

---

## 4. 3단계 — 유사도 맵 구축

사용자가 선택한 카드 집합(N개) 안에서 **가능한 모든 쌍**(N×(N-1)/2개)의 코사인 유사도를 미리 계산해 조회 가능한 형태(맵/딕셔너리)로 저장합니다.

```
for i in 0..N-1:
  for j in i+1..N-1:
    score[i,j] = cosine_similarity(cards[i].embedding, cards[j].embedding)
```

**여기서 점수(score) = 코사인 유사도 원값 그 자체입니다.** 다른 신호(예: 같은 출처인지 여부)를 섞거나, 이 집합 안에서의 최소~최댓값으로 다시 정규화(min-max normalize)하지 않습니다. (과거 버전에서 정규화를 했다가 "이번에 어떤 카드들과 같이 골랐는지에 따라 같은 카드 쌍의 점수가 달라지는" 문제가 발견되어 제거되었습니다 — 이 부분은 재구현 시에도 그대로 지켜야 하는 설계 결정입니다.)

---

## 5. 4단계 — 완전 연결(complete-linkage) 계층적 응집 군집화

**목표**: 선택된 카드 N개를, "묶음 안 모든 카드 쌍의 유사도가 기준선(`MERGE_THRESHOLD`, 기본 0.5) 이상"이라는 조건을 지키면서 최대한 큰 묶음들로 나눕니다.

**의사코드**:
```
clusters = 카드 N개를 각각 크기 1인 묶음으로 초기화

반복:
  두 묶음(i, j)의 모든 조합에 대해:
    linkage(i, j) = min( score[a,b] for a in cluster_i.members, b in cluster_j.members )
    # = 두 묶음 사이에서 "가장 안 닮은 쌍"의 점수 (완전 연결의 정의)

  best = linkage(i,j)가 가장 큰 (i, j) 쌍을 찾음
         # 동점이면 먼저 발견된 조합을 사용 (탐색 순서: i 오름차순 → j 오름차순)

  만약 best의 linkage < MERGE_THRESHOLD:
    반복 종료  # 더 이상 합칠 게 없음

  클러스터 i와 j를 하나로 합침 (병합 로그에 기록: 어떤 두 묶음이, 어떤 점수로, 
    묶음 사이 최솟값을 만든 "가장 안 닮은 카드 쌍"이 무엇이었는지)

묶음이 1개 남거나 더 합칠 수 없을 때까지 반복
```

**핵심 성질**: 이 방식(완전 연결)은 최종 묶음 안의 **모든 카드 쌍이 반드시 기준선 이상**이라는 걸 구조적으로 보장합니다. (참고: "평균 연결"—linkage를 평균으로 계산—방식은 서로 안 닮은 카드끼리도 사슬처럼 연결되는 chaining 문제가 있어 채택하지 않았습니다. 재구현 시에도 평균이 아니라 **최솟값**을 써야 합니다.)

**복잡도**: 매 반복마다 모든 묶음 쌍 × 각 쌍의 모든 멤버 조합을 검사하므로 대략 O(N⁴) 수준입니다. 선택 카드 수가 수십 개 이내(현재 프로그램은 최소 4개부터 사용)라 문제 없지만, 카드 수가 크게 늘어나면 최적화(예: 최솟값 캐싱)가 필요할 수 있습니다.

**병합 로그에 남겨야 할 정보** (8단계에서 사용):
- 몇 번째 병합 단계인지
- 합쳐진 두 묶음 각각의 멤버 id 목록·라벨 목록
- 이 병합을 결정지은 "가장 안 닮은 쌍"의 두 카드 라벨과 그 코사인 유사도
- 병합 점수(= 그 쌍의 코사인 유사도)

## 6. 5단계 — 같은 도메인 그룹은 화면 결과에서 통합

완전 연결은 엄격해서, 실제로는 같은 도메인 카드들인데도 여러 개의 작은 묶음으로 쪼개질 수 있습니다. **군집화 결과 자체(4단계)는 건드리지 않고**, 최종적으로 추천할 도메인이 같은 묶음끼리만 화면 표시용으로 다시 합칩니다.

```
각 묶음(cluster)에 대해:
  도메인별 카드 개수를 센다
  가장 많이 나온 도메인(들, 동점 포함)을 "대표 도메인 집합"으로 삼는다
  대표 도메인 집합을 정렬해 이어붙인 문자열을 그룹 키로 쓴다 (예: "이커머스·물류" 또는 "B2B AI·SaaS+이커머스·물류")

같은 그룹 키를 가진 묶음들을 하나로 합친다
  (합쳐지기 전 원래 묶음 개수는 "하위 묶음 개수"로 따로 기록해서 나중에 사용자에게 투명하게 보여줌)
```

## 7. 6단계 — 도메인별 "선택 비율" 계산 (카드 개수 편차 보정)

도메인마다 원래 카드 총량이 다르므로(예: 핀테크·금융 13개 vs 미디어·저널리즘 4개), "몇 개를 선택했는가"라는 절대 개수 대신 "그 도메인 카드 중 몇 %를 선택했는가"라는 비율을 씁니다.

```
domain_selection_ratio(묶음의 멤버들):
  도메인별 개수를 센다
  가장 많이 나온 도메인(들, 동점 포함)을 대표 도메인으로 삼는다
  각 대표 도메인에 대해: pct = (이번에 뽑힌 개수) / (그 도메인 전체 카드 개수, DOMAIN_DECK_SIZE)
  picked_sum = 대표 도메인들에서 뽑힌 개수 합
  total_sum  = 대표 도메인들의 전체 카드 개수 합
  ratio = picked_sum / total_sum
  반환: ratio (0~1), 그리고 사람이 읽을 문구를 위한 도메인별 세부 내역
```
`DOMAIN_DECK_SIZE`는 전체 카드 77개를 도메인별로 미리 집계해둔 값입니다(1장의 카드 데이터에서 직접 계산 가능).

---

## 8. 7단계 — "주요 추천" vs "참고용" 분류

```
각 묶음의 ratio를 6단계 공식으로 계산해 배열로 모은다
max_ratio = 이 중 최댓값
cutoff = max_ratio × PRIMARY_RATIO   (기본 PRIMARY_RATIO = 0.5)

각 묶음에 대해:
  만약 (멤버 수 >= PRIMARY_MIN_SIZE) 그리고 (이 묶음의 ratio >= cutoff):
    "주요 추천"
  아니면:
    "참고용"
```
기본 상수: `PRIMARY_MIN_SIZE = 2`, `PRIMARY_RATIO = 0.5`.

---

## 9. 8단계 — 추천 결과 구성 (그룹 하나당)

각 "주요 추천"/"참고용" 묶음마다 아래 값을 계산해 결과로 반환합니다.

| 필드 | 계산 방법 |
|---|---|
| 추천 도메인 (`fieldLabel`) | 도메인 다수결 — 가장 많이 나온 도메인(동점이면 전부) 이름을 사람이 읽기 쉬운 설명 문구로 변환(9.1절 매핑표 참고). 동점이 2개 이상이면 " + "로 이어붙임 |
| 평균 의미 유사도 (`avgCos`) | 묶음 안 모든 카드 쌍의 코사인 유사도 평균 |
| 도메인이 섞인 경우의 근거 쌍 | 대표 도메인이 2개 이상이면, **서로 다른 도메인에 속한 카드 쌍 중 코사인 유사도가 가장 높은 쌍**을 찾아 근거로 제시 (AI가 "왜 비슷한지"를 직접 설명해주지는 못하므로, 실제 계산값 중 근거가 되는 쌍을 그대로 보여주는 방식) |
| 가장 강한 연결 (`topPairs`) | 묶음 내 카드 쌍을 유사도 내림차순 정렬해 상위 3개 |
| 가장 약한 연결 (`weakestPair`) | 묶음 내 카드 쌍 중 유사도가 가장 낮은 쌍 — 완전 연결 방식에서는 "이 묶음의 모든 쌍이 최소 이 값 이상은 비슷하다"는 보장선. 단, 5단계에서 화면 통합으로 합쳐진 경우엔 기준선 미만일 수 있음(그 경우 문구로 구분 표시) |
| 병합 단계 서술 | 4단계 병합 로그 중, 이 묶음의 최종 멤버 id를 모두 포함하는 병합 단계만 골라서 순서대로 나열 |
| 선택 비율 근거 | 6단계에서 계산한 ratio를 사람이 읽는 문구로("13개 중 6개 선택(46%)") |

## 10. 상수값 요약

| 상수 | 값 | 의미 | 재구현 시 |
|---|---|---|---|
| `MIN_SELECT` | 4 | 추천을 받으려면 최소 몇 개 선택해야 하는지 | UI 정책값, 자유롭게 바꿔도 됨 |
| `MERGE_THRESHOLD` | 0.5 | 5단계 군집화 기준선 | **⚠️ 검증되지 않은 출발값입니다.** 원본 v3에서 그대로 가져온 값이고, v4 카드 문구로 재실험이 필요한 상태입니다. 동일 모델을 쓴다면 이 값을 출발점으로 삼되, 다른 모델을 쓴다면 반드시 새로 튜닝해야 합니다 |
| `PRIMARY_MIN_SIZE` | 2 | 주요 추천 최소 카드 개수 | 정책값 |
| `PRIMARY_RATIO` | 0.5 | 주요 추천 판정 비율 기준 | 정책값 |

## 11. 반드시 맞춰야 하는 것 vs 자유롭게 바꿔도 되는 것

**반드시 원본과 동일하게 유지해야 결과가 같아지는 것**
- 임베딩 입력 텍스트 형식(`"{label}: {desc}"`), 풀링(mean), 정규화(true)
- 점수 = 코사인 유사도 원값 그 자체(다른 신호를 섞지 않음, 재정규화하지 않음)
- 군집화 linkage 계산에 **평균이 아니라 최솟값**(완전 연결)을 쓰는 것
- 주요/참고 분류에 **절대 개수가 아니라 선택 비율**을 쓰는 것

**정책값이라 통합 프로그램 사정에 맞게 바꿔도 되는 것**
- `MIN_SELECT`, `PRIMARY_MIN_SIZE`, `PRIMARY_RATIO`
- 추천 결과에 보여주는 문구 톤(9장 매핑표·설명 문장은 참고용이며 원하는 언어/톤으로 다시 써도 로직에는 영향 없음)
- `MERGE_THRESHOLD`는 값 자체는 바꿔도 되지만, **다른 임베딩 모델을 쓴다면 반드시 재튜닝**이 필요합니다(10장 참고)

### 12.2 사용법
1. 새로 구현한 코드에 `cards`의 `embedding`을 그대로 입력값으로 넣습니다(모델을 다시 돌릴 필요가 없습니다 — 임베딩 재현성 문제와 로직 문제를 분리하기 위함입니다, 2절 참고).
2. 각 `case`의 `selected_ids`로 파이프라인을 실행하고, 나온 결과를 `expected` 값과 하나씩 비교합니다.
   - `pairwise_similarities`가 다르면 → 코사인 유사도 계산(3단계) 자체가 틀림
   - `merge_log`/`clusters_after_domain_merge`가 다르면 → 군집화(5~6단계) 로직이 틀림
   - `primary_recommendations`/`reference_recommendations`가 다르면 → 선택 비율·분류(7~8단계) 로직이 틀림
3. 코사인 유사도 값은 부동소수점이므로 완전히 똑같지 않고 소수점 10자리 이하에서 차이가 나는 건 정상입니다. 소수점 2~3자리 이상 차이가 나면 로직을 다시 확인하세요.

### 12.3 케이스를 더 추가하고 싶다면
`notes/fixtures/`에 새 픽스처를 만드는 절차:
1. `src/careerlens-mvp-4.html`을 임시로 복사해, 모듈 스코프 변수들(`CARDS`, `cosineSim`, `buildSimilarityMap`, `clusterCards`, `mergeSameDomainClusters`, `domainSelectionRatio`, `splitPrimaryAndReference`, `buildRecommendation` 등)을 `window.__CL = {...}`로 노출하는 한 줄을 "초기화" 섹션 바로 위에 추가합니다(원본 파일은 건드리지 않습니다).
2. 로컬 서버로 이 임시 파일을 띄우고, Playwright(또는 다른 브라우저 자동화 도구)로 페이지를 열어 `window.__CL.CARDS[0].embedding`이 채워질 때까지(모델 로딩 완료) 기다립니다.
3. `page.evaluate()`로 원하는 카드 조합에 대해 3~9단계 함수를 직접 호출해 결과를 뽑고, JSON으로 저장합니다.
